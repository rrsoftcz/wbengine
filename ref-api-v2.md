# WBengine 4.0 API v2

Status 2026-10-26: API-01 to API-04 implemented; content operations have a transactional audit, ETag and cache invalidation. Image availability depends on an explicit safe storage, the box catalog on local registration.

## Controller and contract

`Api -> Api\V2 -> V2\Routes/Model/Contract/Problem` uses the current controller and the route/model patterns. The Model extends ModelAbstract, services are created lazily, and arbitrary PHP class or method names are not accepted. V1 stays registered separately.

- `GET /api/v2` and `/api/v2/capabilities`: public minimal API version 2.0, capability flags, the site's supported languages (`i18n.default`, `i18n.locales`) the pagination contract and `search` (the resources with a search filter and its maximum length). No DB connection, server paths or diagnostic versions.
- `GET /api/v2/identity`: HTTPS, Bearer integration key and scope `discovery:read`. Returns the integration's ID/name/scopes, not its key.
- `GET /api/v2/analytics/overview`: HTTPS, Bearer key with scope `analytics:read`, capability `analytics.read` and migration `006-analytics.sql`. Returns a summary for the requested period and time zone, top pages/articles/boxes and lifetime totals. `period.complete=false` marks a period start that precedes the first recorded public view. Daily history is limited by the `analytics.retentionDays` configuration; the endpoint accepts no visitor identifiers.
- Success: `success: true`, `data`, optionally `pagination`. Error: `success: false`, `error.code`, `error.message`. Unknown paths return 404, disallowed methods 405 with Allow. Internal DB errors return 503 with a generic text.

V2 is a server-to-server interface for the central administration server. It provides no browser CORS and OPTIONS returns 405. The web browser talks to the central server, not directly with the site's integration key. HTTPS behind a proxy uses the already configured trusted proxy policy; a random forwarded header is not proof of TLS.

The Contract supports bounded pagination (default 25, maximum 100), JSON object body versus list, size/depth limits and a field whitelist. The mere existence of these helpers does not enable content endpoints; the flags express the operations that are actually implemented.

## Integration identity and installation

The optional SQL migration `002-api-v2-integrations.sql` creates the key and audit tables. It is run by an operator during an explicit schema upgrade, never by a web request. Without the tables, public discovery can keep working, while authenticated identities fail closed with a generic 503.

Keys are issued and revoked on the site by a logged-in local administrator through the "Integrations" screen (`Wbengine\Box\Integrations`), or by trusted local PHP code with `Api\V2\Model::provision($adminUserId, $name, $scopes)` and `revoke`. The current `ADMIN` role is always loaded from the DB (`ApiUserModel::getAuthorization`), never from the session, a JWT or a form. There is no public provision endpoint or isolated script.

The migration `migrations/4.0.0/007-api-integration-last-used.sql` (after `002`) adds the column `last_used_at BIGINT UNSIGNED NULL` to `cms_api_integrations`. It is idempotent (it adds the column only if missing) and is run by an operator after a backup, never by a web request. `Model::authenticate()` updates `last_used_at` at most once per 60 s per key with a single conditional UPDATE; a write failure (for example an unapplied migration) never fails the request. `Model::list()` returns only non-secret metadata (`integration_id`, `name`, `created_by`, `created_at`, `revoked_at`, `scopes`, `last_used_at`), never the key or its hash. `Console\Doctor` checks both migrations (`migration.002`, `migration.007`) without DDL.

### Integrations screen

The Box extends `WbengineBoxAbstract` and the application wires it in with a thin subclass in its own namespace (for example `App\Box\Central\Integrations`) and a row in `cms_boxes` on a page with `acl = 1`. The tree ACL distinguishes only a logged-in user, so the Box itself verifies the `ADMIN` role. A logged-out user gets 401, a logged-in user without the `ADMIN` role gets 403.

- GET only shows the status and the list. Every change is a POST with a CSRF token bound to the action (`integrations.issue`, `integrations.revoke`) and with a fresh password confirmation (`User\PasswordConfirmation`). The password is neither stored nor logged anywhere; it is verified in constant time against the user's hash from the session and attempts are limited (5 per user and 20 per IP per login limiter window, then 429 with `Retry-After`). A failed confirmation is written to the audit (`integration.reauth`, `denied`) without form values.
- Preflight (`Api\V2\Preflight`, read-only): `apiV2.enabled`, the tables and the `last_used_at` column (the same requirements as Doctor), a request over HTTPS (including `i18n.baseUrl`), the current `ADMIN` role. If unmet, the page shows specific instructions and no key is issued. DDL is never run in an HTTP request.
- Issuing: `Model::provision()` with the fixed 17-scope profile `Box\Integrations::PROFILE_SCOPES` (discovery, reading and writing of articles, pages, menu, sections, boxes, translations and images, preview, publish). The fixed profile `PROFILE_SCOPES` never contains `analytics:read`, even though `Model::SCOPES` knows it; that is added only by the deliberate "Analytics" choice below. The name is validated (1 to 128 bytes without control characters), the recommended one is `WBengine Admin`. Scopes are displayed in human-readable form (cs, en, keys `wb.integrations.*`).

- Analytics (optional): the issue form has an "Analytics" choice (`analytics=1`). When checked, it adds the scope `analytics:read` to the fixed profile (`Integrations::scopesFor(true)`, 18 in total; without the choice exactly 17 scopes are issued as before). The server reads the parameter only as a boolean (`1` checked, empty or `0` not, any other value is 400) and never reads the scope list from the client. The choice is offered only when analytics is usable: `Config::getAnalyticsSettings()['enabled']` is `true` (`analytics.enabled = true` in `Settings.json`) and the schema of migration `migrations/4.0.0/006-analytics.sql` exists (`Doctor::SCHEMA_ANALYTICS`, check `Preflight::analyticsProblems()` via `MigrationStatus` without DDL). Otherwise the field is disabled, next to it are the steps for enabling it and a link to the documentation, issuing without analytics keeps working, and if the client sends the choice anyway, the server responds 400 (`error.analytics_unavailable`) and issues and writes nothing. Analytics problems (`analytics_disabled`, `analytics_schema`, `analytics_database`) never block issuing a key. After issuing, the permission list is collapsed with a count of 17 or 18, `analytics:read` is displayed as "Read the site's visitor overview", and such a key has the label "Analytics" in the key list. On rotation, the choice is prefilled according to whether the key being replaced had analytics. A key's scopes are never changed later; adding or removing analytics means a new key.
- The raw key appears only in the body of the POST response with `Cache-Control: private, no-store` and `Referrer-Policy: same-origin` (not `no-referrer`, which causes `Origin: null` on POST forms). PageCache and FragmentCache are bypassed. The key is not in the URL, log, audit, session or cache. The page shows the site address, the recommended name and the key with a Copy button (clipboard, no persistent browser storage) for registration in the central Admin.
- Rotation: issue a new key (optionally marking the integration being replaced), verify it in the central Admin and only then revoke the old one. The Box revokes nothing automatically. The scopes of an existing key cannot be changed; different scopes mean a new key.
- Revocation: a POST with the password via `Model::revoke()`, effective immediately. If the audit fails, both issuing and revocation are rolled back.

A new key has a cryptographically random part, is returned once, and the DB stores only its SHA-256 hash. Every request verifies the active row, so revoke takes effect immediately. The scope whitelist is finite, and an identity that is too broad does not by itself create an unsupported endpoint. Rotation means a new key, updating the central connection and then revoking the old one.

Provision/revoke and their audit commit together. The methods require an inactive connection: an already open transaction is rejected with `nested_transaction` 409 and must not commit or roll back the caller's work. The guard uses the supported SQL transaction contract, not a nonexistent public mysqli server_status flag. Tests verify both BEGIN and autocommit(false) and the subsequent rollback of the original data. If the revocation audit fails, the key stays active.

The audit distinguishes integration_id, the local administrator and the optional `X-WBengine-Actor`. The latter is merely a bounded, untrusted attribution label of the central administration user, never a reason for authorization. Keys and request bodies are not put into the audit. Missing credentials or scope are audited; an audit failure does not issue an allowed identity. Failed authentication is limited through the existing limiter by the trustworthily determined IP before an audit is added. The local Model::pruneAudit requires a real ADMIN role and has bounded retention and batch size; running it regularly is an operational task.

## Wiring before the CMS

Set `apiV2.enabled` to JSON boolean true. After the accepted custom routes, before the locale redirect, the cache and the CMS, the Application lazily uses its Api controller and its V2/Routes. The prefix is exactly /api/v2 or /api/v2/; a query does not create it. No CMS API page is needed; deleting or moving it does not disconnect the connector. Without the opt-in, the original CMS API wiring works. Custom terminal routes keep their priority. Discovery without CMS rows does not open the DB/session, create boxes or CORS.

For content, apply SQL002, 003, 005 after a backup. The schemas must use InnoDB; the runtime performs no DDL. All protected responses are private, no-store. Send the exact strong quoted ETag in If-Match: missing returns 428, stale 412. After a conflict, reload the current state and merge the changes; do not blindly repeat the write.

## Content resources

For articles/pages/menu/sections/boxes: GET collection, POST create, GET detail /{id}, PATCH update and DELETE with If-Match. Scope {resource}:read/write. Collections use page/per_page, default 25, max 100. Unknown fields and incorrect types are rejected. The complete finite list of fields is in Resources.php. Boolean values are the numbers 0/1.

Search: `GET /pages?search=<text>` filters by title or link and `GET /boxes?search=<text>` by name (a case-insensitive substring; blank text means no filter). The text is at most 100 characters without control characters, otherwise `invalid_search` (400). It uses a prepared LIKE with the wildcards `%`, `_` and `\` escaped, and works with `page`/`per_page`; `pagination.total` counts the matches. Other resources ignore it. Capabilities list it under `search`.

Read-only derived fields: a box row (list and read) also carries `module`, `method` and the boolean `renders_articles`; a page read carries `article_box_ids`, the ids of the boxes visible on the page (its id in the box `sites`, or `shared=1`, the selection `Section\Model` uses) that render articles. None of them is writable: sending any of them is rejected as an unknown field. A box renders articles when its registered type has `renders=article` (fifth argument of `BoxRegistry::register`, `['renders' => 'article']`, also shown in the discovery catalog) or, for a box that is not registered, when its method is `getArticleBox` or its module is `Article` (case-insensitive), the names of the framework article renderer `Box\Article`.

Device limits: `cms_boxes.device_min` (0 any, 1 mobile, 2 tablet, 3 desktop) and `device_strict` are enforced when the page is rendered (`Section\Model::visibleOnDevice`). A box is hidden when `device_min > 0` and the device is below it, or when `device_strict=1` and the device is not exactly `device_min`. The stored default `device_min=1, device_strict=0` shows a box on every device. The full page cache key contains the device type (`page:<locale>:<host>:d<1|2|3>:<path>`), so a page is cached once per device class; the box row cache stays device independent and the filter runs after it. Shared HTTP caches in front of the site should vary by `User-Agent` for pages with device limited boxes.

The box type comes only from the discovery catalog. Trusted startup registers e.g. `BoxRegistry::current()->register('story','Blog','Story',['variant'=>['full','compact']],['central'])`. The default catalog is empty. The client does not choose a PHP class, module or method; settings are registered enum values. Changing section.key and recovery re-validate all attached boxes against the namespace. Registration must be done before run(). An executed box reads the decoded values through `$this->getSettings()` or `$this->getSetting('variant', 'full')`. An old schema without api_settings and invalid JSON return empty settings/the default. The decoder does not accept objects with nested logic and has size/depth limits; the enum registry continues to guard the API. Section loads the internal b.* row so that a new optional column need not require a probe SQL nor break the old schema. The cost is that future boxes columns will also enter the internal row cache.

Articles POST requires title, introtext, bodytext and defaults to Markdown. It creates an empty reservation with site_id 0; the actual content and the target page remain in a private draft. PATCH changes the draft; the live article does not change. The detail has translations and draft:null or content/translations/revision_id; the collection has has_draft/draft_title. Changing the text of legacy_html requires an explicit content_format=markdown and replacing both text fields. Unchanged trusted old HTML and metadata can be preserved. The source field is optional free text (max. 255 characters, without control characters \x00 to \x1f and \x7f, otherwise invalid_source); an empty value or null is fine. On display, only an http(s) URL, a local path starting with a single / or an anchor # becomes a link; everything else (including javascript: and data:) is printed as escaped text.

- GET /articles/{id}/revisions: paginated immutable revisions.
- POST /articles/{id}/restore with {revision_id}: a new copy into the draft, articles:write and the article's ETag.
- POST /articles/{id}/publish with an empty JSON object: articles:write+publish:write and an ETag. Atomically publishes the content/translations, verifies the existing page and rejects a second article on the same page.
- GET /articles/{id}/preview?locale=cs: articles:read+preview:read, private title/introtext/bodytext, safe Markdown; old HTML is escaped. No PHP or template code from the content is executed.
- GET /articles/{id}/metrics: views without an ETag. Site visits therefore do not block editing or publishing.

DELETE of an article keeps the audit/revisions, but the API has no article undelete. Before deleting, back up or keep a revision in the operational procedure.

GET/PUT/DELETE /translations/{site|menu|article}/{id}/{locale} require translations:read/write and the parent's scope. PUT/DELETE use their own translation ETag from GET. Article translations are drafts, site/menu are a direct transactional write with history. Locale e.g. cs, en, en_US.

## Structure recovery

GET /{pages|menu|sections|boxes}/{id}/changes returns paginated complete snapshots and a recovery ETag even after deletion. POST to the same path with /restore and {change_id} requires the write scope and precisely the ETag from changes, not the ordinary detail ETag. The token covers the current row, all translations and the last event. Restoring a previous/initial snapshot can bring back a deleted ID and translations, re-validates references and the current box catalog, and atomically attaches the audit and a new recovery event. A stale snapshot must not overwrite concurrent changes.

## Images

A permanent absolute `apiV2.imageDirectory` or WBENGINE_IMAGE_DIR must be outside DOCUMENT_ROOT. Without it, discovery reports images as unavailable. POST /images takes {base64,mime}, at most 512 KiB PNG/JPEG/WebP, scope images:write. GET collection/detail /images/{opaque-id}, GET /content returns metadata+base64, DELETE requires an ETag and the write scope. The metadata has image_id, mime, size, sha256, created_at, url, public:true.

The file is created under a random opaque ID outside the public filesystem, and stage/rename is tied to the transaction. GET /media/{id} publicly serves only existing metadata+a file with a matching hash/MIME, nosniff and a fixed name. These are public media, not secret draft attachments. The structure and MIME check is not a full pixel decoder or an antivirus; do not use it as a general file upload. The external proxy must have a matching limit on the JSON request body.

## Change log and audit

Every write path records one row in `cms_api_changes` (migration `4.8.0/008-change-log-source.sql`, apply after 002 and 005): API v2 (`source` `v2`, same transaction as the content change), API v1 user, section, translation and cache flush writes (`v1`, actor is the local user id in `local_user_id`) and the CLI commands `user:create|password|delete` and `audit:prune` (`cli`, actor `cli:<operating system user>` in `central_actor`). A row holds the resource, resource id, action, before and after data (JSON), the actor and the time. Rows from sources other than v2 go through redaction: any key named password, token, secret, key or hash (also `ac_key`, `apiKey`, `key_hash`) is stored as `[redacted]`, a section `key` excepted. Password changes are recorded as `passwordChanged: true` only. v2 data is stored as given because structure recovery replays it. Rows written by v1 and the CLI use singular resource names (`user`, `section`, `translation`, `cache`, `audit`) and `integration_id` 0, so they never appear in `/changes` of a v2 resource. Before migration 008 is applied, the new columns are skipped and v2 keeps working as before.

Failed writes: an authenticated integration whose write is refused (validation, not found, conflict, 412 or 428 precondition) gets a `cms_api_audit` row with outcome `rejected` and the error code in `detail`. A 5xx failure is logged to `error_log` with a short reference, the client receives the same reference in the message, and the audit row has outcome `error` and `detail` `ref:<reference>`. No request body and no IP address is stored. Unauthorized and forbidden requests keep their existing outcomes.

Retention (`Settings.json`): `audit.retentionDays` (default 365, 30 to 3650) for `cms_api_audit` and `cms_api_changes`, and `audit.revisionRetentionDays` (default 365, 30 to 3650) for `cms_api_revisions`. Invalid values raise an error when the settings are read. Nothing is deleted automatically: run `audit:prune [--days=N] [--dry-run]` from cron. `--days` overrides both keys. The newest change of every resource and every revision still referenced by a draft are kept, so ETags and recovery keep working. `audit:list [--limit=N] [--resource=NAME] [--actor=ACTOR]` prints recent changes (default 20, at most 500) without their before and after data; `--actor` matches the actor label exactly, or the local user id when numeric. There is no HTTP endpoint for reading the change log yet.

## Cache and transaction boundaries

Content writes, publish, recovery, translations and media require their own transaction and InnoDB, hold the necessary locks and audit atomically. A post-write check prevents silent MySQL truncation. Only after the commit is the shared WBengine data, fragment and page cache invalidated with Cache::flush. A rollback does not report false success. An external CDN is not purged automatically; set up an operational purge. Direct external SQL must provide the same invalidation itself.

The review of regressions covers disallowed legacy HTML writes, the volatile views ETag, namespace bypass on section rename and concurrent translations during recovery. The content API suite 58/331 and lifecycle 36/256 passed. The current shared suite of the whole core without Smarty/Texy: 1981 tests/5596 assertions, 15.250 s, 48 MB, PHP 8.4.27/MySQL 8.4.
